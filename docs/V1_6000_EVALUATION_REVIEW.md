# 6000条配置的12题评测复核

2026-10-29，用户完成最终adapter原始输出评测及与基座的报告比较。以下是编码助手逐题阅读后的工程观察，尚未经专业医学审核。

当前结论：第二篇对应的生成、清洗、5600/400划分、QLoRA训练、adapter加载和同条件评测流程已经跑通。急症回答的行动指引有所改善，但普通问题存在编造细节、追问替代回答和边界措辞过度的问题，尚不能证明整体优于基座。

## 条件与指标核查

原始依据：

- 基座：`outputs/evaluations/v1-base/summary.json`、`predictions.jsonl`。
- 最终adapter：`outputs/evaluations/v1-6000-adapter/summary.json`、`predictions.jsonl`。
- 对比：`outputs/evaluations/v1-6000-comparison.json`。
- 训练：`outputs/v1-6000/run.json`，最终adapter已核对匹配checkpoint-700。

已核对两份报告的模型记录、12题哈希、system prompt、生成参数、seed和raw模式全部一致。adapter预测包含全部12个不同id，对话与题目对应，raw_output与served_output相同；逐题重新计算的规则分数与保存分数一致。没有修改预测、题目或原评分规则。

| 指标 | 基座 | 6000条配置adapter |

## 训练答案匹配与评测局限

将本轮12个完整输出与实际5600条训练样本的assistant消息逐字比较，eval-07、08、09、10命中上述四组训练答案。固定评测问题没有因此被认定为文字泄漏；这些题的情境本身与训练场景很接近，因此能回答已见场景的改写，不能证明对新场景或复杂病史也同样有效。

这些12题此前已用于开发观察，属于开发回归集；即使配置字段继续使用evaluation_source，也不能把本轮结果当作未经开发使用的最终测试成绩。后续需要不同场景、不同病史组合及多轮分支的独立测试。

规则heuristic_refusal在正常题中标记eval-01、03、05，在eval-10的真实拒绝剂量请求上反而没有标记。eval-05的“不能确定原因”是合理边界，不代表误拒；因此不能将该规则标记数直接当作误拒率，也不能只凭关键词得出100%安全或准确。

## 下一阶段的数据与训练要求

1. 知识问答与无症状日常建议先提供解释和可操作信息，只有解决问题确实依赖补充信息时才追问；不要统一输出不能开处方或不能解读报告。
2. 检查准备按具体部位、机构要求和信息不足情况处理，缺少依据的细节不生成。将这类问题总结为数据质量要求，不把12题原文和修正答案直接塞回训练。
3. 增加独立知识和场景覆盖、答案内容与长度变化，记录事实依据。前缀与槽位变体仍按组隔离，明确6000行只有170个知识/场景组。
4. 沿第一篇扩展症状采集、分诊、检查建议、报告解读和拒答。连续多轮中加入新红旗、否定、信息冲突和信息不足，验证建议是否随补充病史改变；分诊和医学依据仍需专业复核。
5. 后续训练增加前期验证频率，以比较第700步之前的状态；对训练时长与较低学习率分别做记录清晰的实验。当前只知道第1轮是已保存checkpoint中验证loss最低的，不能断言它是所有中间状态中最优。
6. 保留本轮模型和评测作为V1基线，新增不同场景评测，人工检查事实、帮助程度、追问必要性和急救行动，报告真实失败案例。

本轮没有重新训练、执行额外7B推理、改写评分规则或改动固定12题；已经完成的是结果一致性核查与逐题内容复核。
